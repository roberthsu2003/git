# 請 AI 幫忙：寫得出需求的提示詞實戰

**延伸實戰 · 第 16 章**　[學習路線](../README.md)

先完成 [AI 開發的 Git 節奏](../日常工作流程/README.md)。那一章管流程（開分支、讀 diff、驗證再 commit）；這一章管開口：同樣的 AI，換個問法，結果差很多。本章所有範例都不指定 AI 產品，複製後把 `[括號]` 換成你的實際內容就能用。

核心觀念只有一句：**AI 沒看到你的螢幕，你給什麼，它就用什麼做事。** 講不清楚範圍，它就用猜的；給了驗收方式，你才有辦法檢查。

## 1. 通用模板：六行寫完一次需求

每次請 AI 做事，先寫這六行，貼在對話開頭：

```text
【背景】我在 [分支名稱]，專案是 [做什麼的]，目前 [哪裡可用、哪裡還沒做]。
【目標】這一輪只做 [一件事]。
【範圍】只能改 [檔案或資料夾]，不要動 [明確列出不能動的]。
【不做】[登入／資料庫／改格式等，這次不做的事]。
【驗收】完成代表 [怎麼檢查、跑什麼指令、看到什麼畫面]。
【輸出】改完列出 [修改檔案、執行的檢查、還沒驗證的部分]，先保留修改讓我檢查，不要自己提交。
```

六行缺一行，AI 就猜一行。最常被省略的是【範圍】和【驗收】，也是出錯最多的地方。

## 2. 範例一：新增小功能

**情境：** 課堂練習專案有一個搜尋頁，想加「空白輸入提示」，不要動其他功能。

❌ 壞指令：`幫我把搜尋功能做好一點。`

問題：「好一點」沒定義，AI 可能順手改掉版面、加資料庫、重寫整個檔案，你讀 diff 讀到哭。

✅ 好指令（可複製）：

```text
【背景】我在 ai/search-page 分支，專案是課堂搜尋頁練習，目前搜尋框可用，還沒有輸入提示。
【目標】這一輪只新增空白輸入提示。
【範圍】只能改 search 相關的一個檔案，不要動版面、登入或資料庫。
【不做】不新增套件、不改其他頁面。
【驗收】空白時顯示提示文字，有輸入時提示消失；我會實際操作確認。
【輸出】改完列出修改檔案與我該檢查的步驟，先保留修改讓我檢查，不要自己提交。
```

你接著做的 Git 動作（見第 08 章）：`git status --short` → `git diff` 逐行讀 → 實際操作驗收 → `git add 相關檔案` → `git commit -m "新增搜尋輸入提示"`。

## 3. 範例二：修 bug

**情境：** 按登入按鈕沒反應，終端機有一段錯誤訊息，你看了半天沒頭緒。

❌ 壞指令：`登入壞了，幫我修好。`

問題：AI 不知道錯誤長什麼樣、怎麼重現，只能通靈，常常把好的程式一起「修掉」。

✅ 好指令（可複製）：

```text
【背景】我在 ai/fix-login 分支，專案是課堂練習，登入頁之前可用。
【現象】按登入按鈕沒反應，終端機錯誤如下（貼上完整錯誤，不要只貼最後一行）：
[貼上錯誤訊息]
【重現】重啟後輸入正確帳密、按登入，必定重現。
【範圍】先找原因，只能做最小修改；不要重寫登入流程、不升級套件。
【驗收】同樣操作可登入，且原本可用的搜尋功能仍正常。
【輸出】先說你判斷的原因與要改哪裡，等我同意再改；改完列出修改檔案與驗證步驟。
```

關鍵差異：**現象＋重現步驟＋完整錯誤** 三件套，外加「先說原因、等我同意再改」。修 bug 最怕 AI 一次改十個地方，你永遠不知道哪一下修好的。

你接著做的 Git 動作：修改前先 `git status` 確認乾淨（起點可確認）；修好後讀 diff，確認只有最小修改，再 commit。

## 4. 範例三：看不懂的程式，請 AI 解釋

**情境：** 接手同學的程式，有一段 50 行的函式完全看不懂，不敢改。

❌ 壞指令：`這段在寫什麼？`（只貼程式，沒說程度和用途）

問題：AI 可能回一篇論文，你還是不知道怎麼下手改。

✅ 好指令（可複製）：

```text
【背景】我是初學者，正在看同學寫的 [檔名]，要接手加一個小功能。
【目標】用我能懂的方式解釋下面這段程式。
【輸出】分三段：1. 它在做什麼（一句話）；2. 逐段解釋（每段不超過三行）；3. 如果我要加 [你的功能]，最可能動哪幾行，為什麼。
[貼上程式]
```

拿到解釋後，不要直接請它改。先自己讀懂，再用範例一的模板開下一輪。這樣 commit 時你才說得出自己做了什麼，交作業的「差異解釋」才寫得出來。

## 5. 範例四：請 AI 幫你想「怎麼驗收」

**情境：** 功能寫完了，但不知道該測什麼，怕漏掉。

✅ 好指令（可複製）：

```text
【背景】我剛完成 [功能名稱]，修改了 [檔案]，專案是 [做什麼的]。
【目標】幫我列驗收清單，不要改程式。
【輸出】用條列式：正常情況測什麼、邊界情況測什麼（空白、錯誤輸入、沒網路）、每一項的預期結果。我會逐項操作打勾。
```

這招適合所有人：AI 出題目，你當考官。逐項操作完，把結果寫進 commit 訊息或 PR 說明，審查的人一看就懂。

## 6. 範例五：Git 卡關，請 AI 幫忙判讀（不幫你下決定）

**情境：** `git pull` 被拒絕，出現 `non-fast-forward`，不知道該 merge 還是重來。

❌ 壞指令：`給我一行指令解決衝突。`

問題：AI 不知道你的分支能不能丟、裡面有沒有要保留的東西，一行指令可能丟掉你的成果。

✅ 好指令（可複製）：

```text
【背景】我在 main 分支，剛剛 pull 被拒絕，顯示 non-fast-forward。
【現況】下面是我實際執行的結果（全部貼上，不要只貼錯誤那行）：
[貼上 git status --short、git log --oneline -5、完整錯誤]
【目標】請判斷是沒分岔還是已分岔，並給我兩種做法的後果；不要直接叫我 force。
【輸出】先說你判斷的依據，再列做法 A（沒分岔時）與做法 B（已分岔時），每種說明會改變什麼、風險在哪。等我選再給指令。
```

原則：**AI 判讀，你決定。** 凡是會改變歷史的（reset、rebase、force），AI 只能給選項，不能替你按 Enter。下指令前，先確認工作區有沒有要保留的修改，這是第 08 章的起點觀念。

## 7. 壞習慣對照表

| 壞習慣 | 為什麼錯 | 改成 |
| --- | --- | --- |
| 做得好一點、修好它 | 沒定義完成 | 寫【驗收】：看到什麼算完成 |
| 一次交代五件事 | diff 爆炸，無法檢查 | 一輪只做一件事，做完 commit 再開下一輪 |
| 不貼錯誤只說壞了 | AI 只能猜 | 貼完整錯誤＋重現步驟 |
| 沒說不能動什麼 | 好的程式一起被改 | 寫【範圍】與【不做】 |
| AI 說通過就 commit | 完成報告不是驗證 | 自己執行檢查、自己讀 diff |
| 直接要一行指令解 Git 問題 | 可能丟成果或改寫歷史 | 先貼 status 與 log，請它判讀給選項 |

## 8. 安全紅線

- 不要貼 API 金鑰、真實 `.env`、帳密、私人資料給 AI；用不含秘密的範例代替。
- AI 給的指令，凡是 `reset --hard`、`rebase`、`push --force`、`clean -fd`，執行前先問自己：工作區有要保留的東西嗎？已分享給別人了嗎？不確定就停手，先 commit 或備份。
- AI 的回答是建議，不是正確答案；`git status` 與 `git diff` 的輸出才是事實。

## 9. 自己做

用第 08 章的 `ai-git-demo`（或任何小練習專案），做兩輪：

1. 用範例一的模板請 AI（或自己扮演 AI）新增 `help.txt` 使用說明，讀 diff、驗收、commit。
2. 故意製造一個小錯誤（例如改壞一行字），用範例二的模板寫一次除錯需求，重點是【現象】【重現】【完整錯誤】三件套。

完成標準：兩筆 commit，每筆只做一件事；你能說出每筆的範圍與驗收方式；交作業時附上你寫的兩次需求原文，以及你實際執行的檢查與結果。
